# Deployment trust boundaries and threat review

AR-003-A · C03 version 1 · 2026-10-19 · proposed for internal security review.

The approved product boundary is a self-hosted installation for **one organization**, with trusted dedicated Linux workers executing untrusted coding tasks under gVisor (`runsc`). Self-hosted means the adopting organization owns deployment and operations. It requires Agent Rewind's own metadata database and artifact store; it does not connect to a customer's production application database. The [supported workflows](WORKFLOWS.md) define filesystem and JSON-policy-state restoration at tool boundaries, with no external side-effect rollback.

This review inspected the application at `8f1ae757005c95c50a789e4fa0a10aae9b3c4024` and delivery checkout `a1d648c`. It did not inspect a live deployment or private data, run a security scan, provision resources or contact a model provider. The [versioned topology fixture](../../contracts/fixtures/trust-boundaries.json) records intended policy. Its passing tests prove internal fixture consistency and selected source properties, not live isolation, compliance or an independent security assessment. SEC/QE and project-lead review remain required; no external security sign-off is claimed.

## Assets, actors and trust zones

| Asset / principal | Authority and exposure | Required boundary |
| --- | --- | --- |
| Organization operator and task submitter | Can submit source, commands, instructions, replacement tool results and grader definitions under current role policy. Input and generated code are untrusted. | Authenticate; authorize project/resource/action; enforce admission limits and budget. A valid login does not make submitted code safe. |
| Viewer / developer browser | Can inspect authorized decrypted source, observations, model responses, evaluation and study results. Browser holds session or API key in memory. | API-mediated access and safe text rendering; no direct DB, object bucket, model key or Docker access. Trace access is source-code access. |
| Organization / deployment administrator | Chooses images, adapters, model endpoint, IdP, encryption key, budgets and operators. Can control infrastructure. | Trusted within the installation; apply least privilege, change review and off-device audit/backup. Hash chains do not defeat an administrator who rewrites DB and objects together. |
| API identity and host | Authenticates users, reads/writes metadata and encrypted artifacts, decrypts traces and signs/encrypts cookies. | No Docker socket, model credential or sandbox execution. Runtime DB identity has DML rights, not DDL. Separate network and workload identity from worker. |
| Trusted worker and Docker daemon | Worker loads plaintext tasks/checkpoints, holds model key, invokes provider, manages Docker and writes captures. Docker group grants powerful host control. | Dedicated hosts without unrelated sensitive services. Worker compromise is a deployment-level incident; gVisor does not isolate the worker from its own credentials. Systemd hardening does not remove Docker authority. |
| Agent sandbox / evaluator sandbox | Candidate code executes with UID 1000 inside `runsc`. Evaluation also imports/executes candidate code and is treated as untrusted execution even though the grader definition is trusted. | No network, credentials, host control socket or arbitrary host bind mounts. Read-only root; bounded disposable workspace, memory, CPU, process count, output and time. |
| Dedicated Postgres metadata | Run/study JSON, jobs, leases, budgets, token hashes, audit, future ownership/projections. Includes sensitive metadata even when blobs are encrypted. | Private routing, TLS, storage encryption, explicit runtime/migration identities, backups and restore tests. Never reuse a customer application DB. |
| Encrypted artifact store and key authority | Source blobs, task manifests, policy state, event/provider payloads, evaluator output; key loss makes history unreadable. API and worker can decrypt. | No public bucket; scoped read/write, encryption and key lifecycle. Current single Fernet key also encrypts cookies; target KMS lifecycle is future work. |
| Identity provider | OIDC issuer, signing keys and claims establish principal/organization role. | Pinned configured issuer/client/audience, PKCE, nonce, expiry and approved HTTPS discovery endpoints; project revocation remains current application authority. |
| Approved model provider | Receives task instruction, visible file names and growing policy/tool-observation context from the trusted worker. | Approved processor/region/data terms, allowed endpoint and worker-only credential. No sandbox network access does **not** mean no data leaves the organization. |
| Cloud identity / migration operator | Workload identity can use an approved platform identity endpoint; migration operator separately holds DDL access. | Platform bootstrap is explicitly profiled at ENV0. Untrusted sandboxes cannot reach metadata endpoints. Runtime roles never inherit migration authority. |

Current TaskSpec lets an operator supply evaluator files and command. “Trusted grader” is therefore an operating assumption, not an implemented approval registry. Research evidence needs the permitted, frozen evaluator identity and protocol from C02/C06; an operator-selected passing command does not establish task correctness.

The internal product project is an authorization scope within one organization, not proof of hostile multitenant isolation. Multi-organization shared hosting, customer network/database connectors, arbitrary adapter loading and process-memory replay remain outside C03.

## Allowed connections and denied paths

The fixture uses default-deny **direct connection** policy. Its 16 components, 15 allowed connections and 40 explicit denials are abstract review inputs, not generated firewall rules. DNS, approved proxy endpoints, platform identity audiences, actual CIDRs and installation-specific operator access must be resolved in C14/ENV0. No placeholder address is permission to open a route.

| Origin | Allowed destination and purpose | Explicitly denied / constrained |
| --- | --- | --- |
| Browser | Authenticated HTTPS ingress; interactive login at the configured IdP. | Direct metadata/object/model access and service credentials. Internal ingress may require VPN/private access; login still required. |
| Ingress | API on private service route. | Public access to worker, DB, bucket or Docker. Bound body/rate/concurrency before expensive work. |
| API | Dedicated metadata DML; encrypted object reads/writes; approved IdP HTTPS endpoints; approved key authority/workload identity bootstrap. | Docker, direct model invocation and customer application DB. No migration DDL identity. |
| Trusted worker | Metadata DML; encrypted object I/O; approved model HTTPS endpoint; key authority and approved platform workload identity bootstrap; local Docker socket. | Customer application DB, arbitrary Internet destinations and inbound public worker/Docker listeners. Bootstrap/image acquisition is a separate operator-controlled supply-chain activity, not task network access. |
| Agent/evaluator sandbox | No direct outbound connection. Docker transports validated data between the trusted worker and private sandbox volumes/output streams. | API, DB, object store, IdP, model endpoint, Internet, cloud metadata, Docker, other sandboxes and customer DB. No credentials or arbitrary host mounts. |
| Migration operator | Explicit, audited maintenance connection to metadata with DDL privilege while compatibility rules permit. | Runtime reuse of migration authority; customer application DB migrations. |

A private network reduces which machines can reach control services, separates worker/control-plane routes, and keeps DB/object/key endpoints off public access. It does not authenticate a user, prove project authorization, stop a trusted worker from misusing credentials, remove model-provider processing or make guest execution safe. No network/database access to the adopter's other applications is needed for the supported workflows.

The policy intentionally distinguishes direct connections from **mediated information flow**. Agent output returns to the worker, may enter the policy's next provider request, and is captured for authorized readers. A malicious task can place sensitive content it legitimately sees into its output. The boundary therefore depends on limiting task inputs, project access and approved provider processing, not merely `network_mode=none`. Redaction is explicit literal capture filtering; original encrypted task manifests and redaction patterns remain worker-readable. Do not submit secrets expecting redaction to remove them from all storage or provider requests.

## Responsibility and unresolved decisions

The deployment operator owns host patching, DB/bucket/key backups, IAM, IdP configuration, network rules, image approval, secret rotation and incident response. The product implements explicit admission, scope, data integrity, budget and sandbox contracts and provides testable installation defaults. Model-provider billing/data behavior remains external; reservations are conservative admission controls, not a guarantee against provider billing changes.

ARCH0 must dispose of the trust boundary, principal mapping, project ownership and compatibility decisions together with C04. ENV0 must name region/residency, permitted cloud/model processors, funded infrastructure, network/identity profile and actual operations owner before provisioning. PARTNER0 must supply permitted source/trace data and evaluator rights. The existing $200 validation ceiling is unchanged; no additional cloud or inference spending is authorized by this document. AR-003-B owns capacity, operating cost and staffing decisions; C14 turns approved topology into deployable infrastructure.

SEC/QE review should explicitly confirm the trusted-worker/Docker boundary, intended provider data egress, guest deny matrix, grader limitation and legacy scope gaps. Record reviewer and disposition in the lead's assignment/decision record. Required independent review at AR-044 and live gVisor/security drills are not replaced by internal review or passing static tests.

## Automated checks and evidence boundary

`tests/test_trust_contract.py` uses only the standard library to validate the versioned fixture, component references, default-deny network policy, forbidden edges, secret recipients and sandbox expectations. Mutation checks reject guest model access, omitted metadata denial, API model-key exposure, Docker-socket mount, unsupported runtime fallback, unknown component and a false live-verification claim. A source AST check separately inspects **both** current Docker container constructors for network-none, non-root/read-only settings, dropped capabilities, no-new-privileges, no explicit privileged mode, constrained environment names and resource-limit arguments.

The AST check does not execute Docker, inspect an installed image, resolve mounts or prove the configured runtime exists. It requires review when a constructor is added or refactored. Fixture network denials are reviewed requirements, not observed packets. This work does not claim the planned TB-01–12 live/adversarial cases have passed.

Recorded validation: the pytest console entrypoint `pytest -q -p no:cacheprovider tests/test_trust_contract.py` and `python3 -m unittest discover -s tests -p test_trust_contract.py -v` each passed all **9 checks**. Scoped Ruff lint/format passed, all local links resolved, and `git diff --check` passed. Existing installed tools were used without dependency installation; no runtime service or provider was started.
